# 语义搜图 tag 优化方案（2026-10-07）

> 起因：用户反馈「语义搜图的关键词不准」。今天（2026-10-07）的台架实测（`semantic-search-model-selection.md`）
> 已把方案定到**tag 提精度 + CLIP 保底（融合）**；本文是**它的落地方案**，并且把
> 「缩略图升 512/WebP 必须全库重跑」这件事合进来 —— 两者必须共用同一趟读盘，否则要多读一遍 165 万张原图。
>
> 本文只写**能验收的动作**。实测读数一律注明来源；估算一律注明算法。

## 〇、结论先看这五条

1. **落地形态 = 加一层，不换主干。** CLIP（SigLIP2-224）保持为唯一「任意中文查询」通道；
   JoyTag 标签倒排作为第二路；两路用 RRF 融合。依据：tag 赢的 13 个概念**全是服饰/物件**，
   CLIP 赢的 6 个**全是场景/姿态/通用外观**，且 tag 有 **4** 个概念**词表根本为空**
   （黑丝/白丝/空姐/停车场 —— 验收实测，`parseQuery().missing` 非空 ⇒ `UNSUPPORTED`）。
   ⇒ 融合实测把 CLIP 返回集的前 10 命中从 **37/270 拉到 87/270**（§M4）。
2. **P0 是词表，不是模型。** 现有 308 词词表英文侧只有 **44.8%（138/308）** 能原样对上 danbooru 标签
   （`tag-coverage.js`），且对得上的一半是「海滩/森林/沙漠」这类**本库一张都没有**的风景词。
   不补词表就上索引，表现为「搜『黑丝』永远 0 结果」——**静默错**。
3. **GPU 闸门已过，而且不用换包**（M2 三条 ONNX 路径**全部验完**：JoyTag dml **9.4×** 且逐值一致；
   CLIP **1.99×** 但 **int8 数值不一致** ⇒ 索引/查询必须同一个 EP；人脸 **0.95×** 不换）。
   实测机器 = **RTX 3060 12 GB**；
   `node_modules/onnxruntime-node@1.24.3` 已自带 **`bin/napi-v6/win32/x64/DirectML.dll`**
   ⇒ 不用装 CUDA，改会话选项即可（现在两处都写死 CPU）。
   CPU 实测单张：CLIP 0.74 s、JoyTag 0.76 s ⇒ 165 万张两路一起 ≈ **29 天**
   （CLIP 14 天 + JoyTag 15 天）；这是全库索引的唯一真门槛。
4. **全库重跑这件事必须「一趟出五样」。** 缩略图升 512/WebP 实测**几乎全库都是待重跑**
   （见 §一 第 4 条）。重跑任务本来就**读原图**（`main.js#regenerateRowsWithConcurrency`），
   所以 tag 推理、CLIP 向量、dHash 都必须挂在**同一次解码**上，边际成本只剩推理本身。
5. **磁盘是硬约束，先算账再动手。** 🔄 **2026-10-07 深夜已把图库数据目录整份搬到 D 盘**
   （`D:\AuroraGallery`，真相源 = `settings.json#dataDir`，迁移逻辑 `src/main/data-dir.js`）——
   这笔账**换了主角**：现在看 **D 盘（64.3 GB 可用）**，三笔账合计 15.7 GiB 装得下，
   **原来「C 盘装不下」的阻塞已解除**。
   ⚠️ 两件没结的：① C 盘仍有 **13.7 GB**，且**还留着一份 18 GB 的旧 `photos.db`**
   （迁移没走「删源」那一步），删它前先确认是不是硬链接（未必真腾出空间）；
   ② 方案期测到的「C 盘一天内少 8 GB、没能定位到是谁吃的」**仍未结案**，C 盘继续掉就得查。
   三笔账：缩略图净增 ≈ **6.8 GiB**、全库 CLIP 向量 ≈ **6.5 GiB**、tag 倒排 ≈ **2.44 GiB**
   （M3 实测 87.7 行/张修正，原估 0.7 GiB），另有 WAL 峰值。
   ⇒ 缩略图与索引**仍然不能同时开跑**，但理由变了：不再只是磁盘，而是「两笔账一起占会让
   失败时归因不清」，而缩略图那半本来就是**独立可回滚**的 —— 先跑完它、确认无红再开索引。

## 二、不许破的六条不变式

1. **CLIP 主干不动。** 它是唯一能接受任意中文、零索引成本的通道；tag 路是**加层**。
2. **「搜不到」必须由 CLIP 兜住。** 词表为空的概念（黑丝/白丝/空姐）由 CLIP 返回，
   不能因为「tag 路没有」就静默 0 结果 —— 融合是**并集**语义。
3. **索引源与查询源同源。** 索引与检索必须走同一份预处理
   （`semantic-worker.js#prepare()`：`rotate → resize(512 inside) → removeAlpha → jpeg`）。
   ⚠️ 换 EP（cpu→dml）会引入 ~1e-4 量级的数值差，**可接受**（远小于阈值间距），
   但必须在索引里留下 provenance（见第 4 条），否则以后无法解释分数漂移。
4. **索引必须记「我是用哪一代源算的」。** 今天学到的教训：缩略图那套有 `thumb_size`/`thumb_format`
   两列可辨混源，**语义索引没有任何字段**（`semantic-worker.js:415` 直接吃 `photo.thumbnail`，
   拿不到就回退原图）。⇒ 混源期（512/webp 与 256/jpeg 并存）里已定档的阈值无法解释漂移。
   新索引表一律加 `source_spec`（`<size>/<format>`）与 `engine`（EP 名）。
5. **「词表表达不了」要显式报出来。** 查询词若在词表里没有 tags，UI 必须显示
   「该词暂不支持标签检索，已仅用语义检索」类似提示，**不许**当作 0 结果。
6. **写路径唯一 + 索引单写者。** 缩略图只有 `database.js#updatePhotoThumbnail(id, buf, spec)` 一条
   （`spec` 缺失时写 `0`/`''`，不沿用旧值）；AI 索引不在 `dbWriteQueue` 提交器里
   ⇒ **必须自带游标 + 幂等 upsert**，否则重启后不会自动补齐（人脸/语义今天就是这样）。

  | 规则 | 零返回 | 平均返回 | 单查询最多 | 地板绑定 |

  | M0 前（固定 0.01，无 α） | 0/27 | 1196 | 4971 | — |

- 🔴 **撤回 `Tmin = 0.002`（本里程碑最重要的产出，是一条方法论）**：
  - 台架的卖点是「零返回 1/27 → 0/27」。**真库上这条卖点不存在**：零返回 ⟺ `top1 < 地板`，
    而真库 top1 最小值 **0.0120 > 0.01** ⇒ 地板 0.01 就一个都饿不死。那个 1/27 是
    **1,500 张子集**的产物（样本少 ⇒ 最大值低）；**规模越大 top1 只会越高** ⇒ 全库更安全。
  - 代价可量：地板绑定 **13/27 → 0/27**（低分查询失去兜底），换 +3.0% 召回，
    而**负对照漏进来**：「汽车」0→5 张、「咖啡」0→1 张（达标 0 张的负对照 4/5 → 2/5）。
  - 台架上 `(0.3, 0.01)` 的 F1 **0.160 本来就高于** `(0.3, 0.002)` 的 0.159。
  - ⚠️ **教训**：台架是对「已算好的分数数组」做过滤，样本量决定 `top1` 的期望 ⇒
    **只在子集上调阈值参数会系统性地偏向「更松」**。改这个数必须跑**两个**：
    台架二维表（`sweep-adaptive.js`）**加** 真库复算探针（`probe-adaptive-live.js`）。
  - ✅ 顺带消解了一个阻塞点：活跃库 `settings.json` 里持久化的 `aiSearchMatchThreshold` 是 `0.01`，
    与代码默认值一致 ⇒ **不需要任何迁移**。（该文件是**默认值全量落盘**，49 个默认键一个不缺 ——
    这正是「改代码默认值对已装库不生效」的机制，换默认值时必须同时想迁移。）
- **α 取 0.3 是拐点选择，不是 F1 最优**：Tmin=0.01 行上 α∈[0.2, 0.3] 的 F1 只差 0.002
  （0.162 / 0.160，噪声范围内），而平均返回 1013 → 646（−36%）；再往上开始真亏
  （0.4 时 F1 0.154、0.5 时 0.140，「有命中」也从 22/27 掉到 20/27）。
- **关键算法洞察（写进了代码注释）**：`effective ≥ threshold` 恒成立 + 有界截断必然保住最大值
  ⇒ **不需要为求 top1 再扫一遍向量**（点积是这个方法的全部成本），`kept[0]` 就是真 top1。
  连带三条既有契约必须同时满足（都踩过）：
  ① `threshold === 0` 时自适应必须让路（用户滑到 0 = 「我全都要」）；
  ② `matched` 在自适应未生效时必须用流式 `candidates`（**不受 maxResults 影响**）；
  ③ `truncated` 只表示「受返回上限限制」，**不含**被自适应砍掉的那批（那是「不达标」）。

1. **只截断 tag 路，CLIP 全量参与**。直觉写法「两路各取前 200」会让结果**变少**

## 四、tag 索引的数据结构（草案）

```sql
-- 单库单写者；与 CLIP 索引分表，便于分别重建
CREATE TABLE tag_meta (k INTEGER PRIMARY KEY CHECK (k = 1),
  source_spec TEXT,     -- '512/webp' —— 这一代索引的源规格（不变式 4）
  engine TEXT,          -- 'dml' | 'cpu'
  model TEXT,           -- 'joytag'
  vocab_key TEXT,       -- 词表版本（M0 的表变了要能判废）
  updated_at INTEGER);

CREATE TABLE tag_vocab (tag_id INTEGER PRIMARY KEY, tag TEXT UNIQUE NOT NULL);
CREATE TABLE photo_tag (
  photo_id INTEGER NOT NULL,
  tag_id INTEGER NOT NULL,
  score INTEGER NOT NULL,   -- 量化到 0–100（原值 ×100），省 3 字节/行
  PRIMARY KEY (photo_id, tag_id)) WITHOUT ROWID;
CREATE INDEX idx_tag_score ON photo_tag(tag_id, score DESC);   -- 倒排：按标签取前 N
```

- **只存「超过入库阈值」的标签**（建议 `score ≥ 0.15`，与 `TAG_THRESHOLD` 对齐），
  不存 5813 维全量浮点。按平均 25 个标签估算：1,656,580 × 25 ≈ **4,140 万行**，
  每行 ≈ 10 B（`WITHOUT ROWID` + 量化）⇒ 主表 ≈ **0.4 GiB** + 索引 ≈ **0.3 GiB**。
- **必须幂等**：`INSERT OR REPLACE`（重跑同一张不得产生重复行，守护断言）。
- **不放进 `photos.db`**：它正在被缩略图重跑高频重写，混在一起会让 WAL 与 checkpoint 互相拖累。

## 五、查询侧算法（可直接照着实现）

1. **词表解析**：中文查询 → `{tags, mode}`。`mode='any'` 时标签间取并集、`'all'` 取交集；
   词不在词表或 `unsupported` ⇒ 该路**不参与**（并标记，供 UI 提示）。
   实现：`src/ai/tag-fusion.js#parseQuery`。
2. **tag 路打分**：对候选图片取「命中标签的分数之和」或「最大分」（建议最大分 + 命中数做 tie-break）；
   过滤 `score < 0.55`。实现：`src/ai/tag-index-store.js#query`（`any` 取 MAX、`all` 取 MIN）。
3. **CLIP 路**：基线差 `adjusted = dot(q, v) − generic_sim`，过滤 `≥ max(0.002, 0.3 × top1)`。
4. **融合**：RRF，`K = 60`，同 `photo_id` 累加 `1/(K + rank)`。
   🔴 **修正（实施时发现的错，2026-10-07）**：本节原先写「两路各取前 200 参与」——**这是错的**。
   CLIP 路的返回上限是 5,000，截到 200 之后用户从「找到 3,000 张」变成「最多 400 张」，
   是一个纯粹的回退，而且**长得不像 bug**（数字变了而已）。真正存在的约束只有一条：
   **tag 路的候选要按 id 回主库补图片行，而那条 SQL 是 `IN (?,…)` 展开的**（SQLite 参数上限 32766）
   ⇒ 该截断的是 **tag 路**（`FUSE_DEPTH = 200`），CLIP 全量参与。
   深度外的 CLIP 条目 `rrf = 1/(K+rank)` 在数值上**必然**小于任何进了头部的条目
   （头部最小的也 ≥ `1/(K+200)`），所以它们自动排在后面且保持原序 —— 不需要写「尾部拼接」，
   也就没有「忘了拼尾部」。
5. **结果标注来源**：每条结果携带 `route: 'tag' | 'clip' | 'both'`（页面显示 + 回归断言）。

## 九、风险与静默失败清单（前三条是今天验证缩略图迁移时抓到的通用模式）

1. **字节与 Content-Type 不同源** ⇒ 浏览器不报错、只是什么都不显示。
   已修：`thumbMimeType(row.thumb_format)` 按行派生；6 处服务端全部派生；
   唯一写路径 `updatePhotoThumbnail` 无 spec 时写 `0`/`''`。**新加任何写路径都必须带 spec。**
2. **缓存键不带「本行规格」** ⇒ 重建到一半时「同一张图片两副面孔」。已修：两端键 = `photoCacheVersion + '-' + size + format`。
3. **收敛 ≠ 成功**（队列按批无条件删除、失败只累加计数）⇒ 判「跑完」必须同时看 `failed`。
4. **索引混源无处可辨**（不变式 4）⇒ 新索引从第一天就带 `source_spec`/`engine`。
5. **词表恒空被当成 0 结果**（黑丝/白丝/空姐）⇒ 必须显式 `unsupported` + UI 提示。
6. **`thumb_size` 是「请求档位」不是「实际像素」**（`withoutEnlargement`）⇒ 小原图 / ICO / RAW 内嵌小预览
   达不到 512 但记录 512。当前无下游依赖真实像素（表里没有 thumb 宽高列），**不影响正确性**；
   但语义索引契约里「索引源 = 256px」这句话要改成「源 = 缩略图，实际 ≤ 请求档位」。

| 缩略图 | ✅（仅**缺**的行） | ✅（**规格 ≠ 目标**的行，从原图重出） |
| 原图尺寸 `width/height` | ✅ `updatePhotoDimensions` | ❌ |
| 拍摄参数 EXIF | ✅ `updatePhotoExif` | ❌ |
| dHash（视觉指纹） | ✅ `updatePhotoDhash` + buckets | ❌ |
| SHA-256（查重指纹） | ✅ `updatePhotoHash` | ❌ |

重建那条路只有一行写库：`db.updatePhotoThumbnail(...)`。**它是补全的子集 + 不同谓词，不是超集。**

**技术上要并过来是便宜的**（三点都已核实）：① `thumb-regen-queue.js#FETCH_SQL` 已经取了
`file_size` / `date_modified`（写 dHash / 查重指纹的必需参数），`p` 那一侧本来就是
`SEARCH p USING INTEGER PRIMARY KEY` 回表 ⇒ 再多取几列**不额外读盘**；
② EXIF / 尺寸共用「解码后顺手读一次文件头」，注释里写明是**零额外磁盘 I/O**；
③ dHash 可以直接吃这次解码（`computeDhashFromPipeline(si.instance)`），
**不必再开一次文件** —— 这正是补全那一支省掉 70% 时间的做法。

**代价与取舍（2026-10-08 实测）**：
- 补全第二支残余 **857,372 行**（见 §M5 ⑤）。**不并**：重建跑完（~15 h）之后还要再来一趟
  元数据，重读一遍原图（K:/G: USB 机械盘，读盘是主导成本）。
- **要并就现在并**：重建是 `ORDER BY q.id DESC` 抽干，已处理的那两万多行**全部落在
  id ≥ 1,288,000 的「元数据已齐」区段**（§M5 ⑤ 实测该区段残余 0）⇒ **此刻并进去不丢任何行**；
  等它跑完再并，那 857k 行就真得单独再读一遍。
- 🔴 **查重指纹（SHA-256）单独考虑**：它要把**整份文件**读进内存（`sharedBuf`，按
  `THUMB_SHARED_READ_MAX_BYTES` 闸门），而重建并发 8、本机可用内存只剩 1.28 GB ⇒
  三样里只有它带内存风险。「尺寸 / EXIF / dHash」是无风险的。**要么三样先并、指纹不并，
  要么等内存空出来再说。**
- 并入必须在**重建停下时改代码再重启**（队列持久化，重启接着抽干；`phase='draining'`
  会让登记那一趟直接跳过，不会重扫全库）。

### ✅ 已落地（2026-10-08，用户选择「四样全并」）

- `main.js#regenerateRowsWithConcurrency` 已改成五个写入口；`FETCH_SQL` 加了
  `dhash / width / height / file_hash / exif_mtime / exif_ver`（取批计划不变）；
  顶栏那一节副行报「拍摄信息 / 视觉指纹 / 查重指纹」。
- 顺序契约：**读文件头 → 算 dHash → 最后缩放置换**（`resizeThumb()` 会 `rotate()`，
  dHash 取在它之后 = 位全变）。守护对三者源码偏移做大小断言。
- ⚠️ **合并之后补全的第二支不会自己归零到「有人补过了」**：补全的候选谓词是**按列**的
  （`dhash IS NULL` / `width` / `exif`），而重建只处理**队列里**的行（规格 ≠ 目标）。
  这一次全库都在队列里，所以覆盖得到；**下一次重建时队列可能是空的** ⇒
  那时元数据仍要靠补全第二趟。两条任务的分工**没有合并**，只是共享了这一次读盘。
