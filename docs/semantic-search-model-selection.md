# 语义搜图：模型方案对比测试（2026-10-07）

> 起因：用户反馈「语义搜图的关键词不准」，并要求对比 ① CLIP 双编码器路线（含同族换档）
> ② 常见图片 tag 模型 ③ BLIP 这类描述（caption）模型，用实测数据决定方案。
>
> 本文只记录**能复现的读数与结论**。过程明细在 `.workbuddy/memory/2026-10-07.md`，
> 台架脚本在 `.workbuddy/bench/`（不参与提交）。

---

## 一、结论（先给）

1. **主干不动**：SigLIP2-base-224 保持为语义检索主干。它是唯一「任意中文查询、零索引成本」的通道。
2. **加一层 JoyTag 标签索引**：同一语料上 P@10 从 0.188 → **0.354**（1.9×），R@100 0.296 → **0.538**（1.8×），
   而单张编码成本与现有 CLIP **几乎相同**（0.76 s vs 0.74 s，8 线程），常驻内存 375 MB（CLIP 文本塔 608 MB）。
3. **两者融合（RRF）优于任一单用**：融合后 P@10 0.307（≈ 单用 JoyTag 的 0.315），
   但 R@100 提到 **0.519**、P@50 0.195 → 0.209，**零返回从 6/27 降到 2/27**
   ——CLIP 兜住了 tag 词表表达不了的概念（空姐 R@100 0.00 → 0.18）。
   → 落地形态是 **tag 提精度 + CLIP 保底**，而不是二选一。
4. **不换 SigLIP2-256**：同语料 P@10 0.188 vs 0.188、R@100 0.309 vs 0.296，逐查询互有胜负。
   换档要重跑全库索引（实测 0.74 s/张）+ 重新标定阈值，收益为零。
5. **不上 caption（BLIP / Florence-2）**：单张 4.97 s（BLIP）/ 5.75–6.9 s（Florence-2 detailed），是 CLIP 的 6.7–9.3 倍。
   在**同一 400 张语料**上，R@100 只有 **0.161（BLIP）/ 0.127（Florence）**——现状 CLIP 0.499、JoyTag 0.607——
   零命中从 CLIP 的 1/19 涨到 **9/19 / 13/19**。根因是它们输出的英文通用描述里没有 cosplay 语义
   （400 张里一条都没出现 uniform / maid / qipao），而 JoyTag 直接吐 `maid` / `school_uniform` / `pantyhose`，
   还能认角色。详见 4.5。
6. **不上 WD-EVA02-Large tagger**：单张 3.21 s（JoyTag 的 4.2 倍）、常驻 1238 MB（3.3 倍）——
   这两条是硬证据，足以否掉。⚠️ 但它的**精度本轮没能测出来**（见第六节）：
   我这条 runner 的 WD 分支输出失效（96.5% 的概率挤在 0.49–0.51），读数不可用。
7. **阈值那一半问题：`0.02` 这个方向是错的，而代码里（HEAD）本来就是 `0.01`。**
   所以这条的产出不是改代码，而是**解释用户症状**并指出下一步：`0.02` 会把「排序其实是对的、只是分数不高」
   的概念整条杀成 0 结果（全库实测零返回 6/27，`0.01` 只有 1/27）。真正的解法是自适应阈值。详见第五节。

> 📌 **想看逐条可核对的原始输出**（同一个查询两套方案各返回什么、同一张图四套方案各产出什么、
> 「关键词不准」到底是什么形状）→ **第九节**。那张「同一张图」的表把大部分结论压在一屏里：
> 一张明确的女仆装图片，**CLIP 排第 626 名**（过了阈值但翻不到），JoyTag 给 `maid=0.799` 排第 1，
> 而 BLIP / Florence 的描述里连「围裙」都没有。
>
> 🖼️ **想直接看图** → `.workbuddy/bench/showcase/gallery.html`（2.72 MB 单文件，图片全部内嵌；
> 生成命令见 9.6）。27 个概念逐概念两排缩略图对照 + 12 张大图的四模型输出 + 5 个负对照。

## 二、测试口径

### 2.1 语料

索引库当前覆盖 `K:/COS` 上 **photo_id 324,737–332,328** 这一段连续区间的 **7374 张**
（库总量 1,658,580 张，`MAX(id)=1,981,503`）。这一段全部是真人 cosplay 图包，144 个图包目录，
题材高度集中：制服 / JK / 旗袍 / 比基尼 / 女仆 / 空姐 / 绳艺 / 死库水 / 角色扮演等。

> ⚠️ 索引是**建到一半停下的**（取批 SQL 无任何隐性过滤，游标停在 324,737）。
> 恢复索引会继续往下走，因此「目标规模」不是 7374 而是 165 万——这一点直接决定第五节之外的成本约束：
> 按本次实测的单张成本，**任何逐图编码方案在当前 CPU 实现下跑完 165 万张都要 10 天以上**
> （CLIP 0.74 s/张 ≈ 14 天；JoyTag 0.76 s/张 ≈ 15 天）。这是比「选哪个模型」更根本的约束，
> 见第七节。

因为 WD-EVA02 单张成本太高，另外取了一个 **分层子集**：

| 语料 | 规模 | 覆盖图包 | 用途 |
|---|---|---|---|
| 全库段 | 7374 | 144 | CLIP-224 全量基线 |
| 子集 A | 1500（20%，按包比例分配） | 143 | CLIP-224 / CLIP-256 / JoyTag 三方对比 |
| 子集 B | 600（按包轮转抽） | 143 | 追加 WD14 对比（⚠️ 实际只跑到 259/600 即中止，且该路 runner 输出失效 ⇒ 数字作废，见第六节） |
| 子集 C | 400（子集 A ∩ 全库段中 **id 最小**的 400 张） | — | Florence-2 / BLIP 描述模型 |

⚠️ 子集 C 落在全库段的最前段（id 324737–326779），因此**它的概念构成与子集 A 整体不同**
（例如 `空姐` 在子集 C 里有 17 个正样本，而 `蕾丝`/`死库水`/`猫`/`蛋糕` 为 0）。
后果是：绝对读数会随语料变化（CLIP-224 的 P@10 在子集 A 是 0.188、在子集 C 是 0.295），
**只有同一语料内的横向比较才成立** —— 所以 4.5 节把 CLIP 和 JoyTag 一起重跑到了子集 C 上。
子集 C 的 id 清单落盘在 `%TEMP%/aurora-bench/subset400.json`（由 caption 产物的 id 逆向导出，
已校验 400 张全部属于子集 A）。

### 2.2 查询集（32 个）

**正样本标签来自图包名。** 这个库的图包目录名是人工命名的内容描述
（`NO.007jk黑丝制服`、`NO.055蓝白条比基尼`、`NO.053空姐`、`桃良阿宅NO.056绳艺`…），
是一份**现成的、零标注成本的弱标签**。凡是图包名（作者层 + 包名层）含该概念同义词的图片即为正样本。

- 27 个「库里真有」的概念，子集 A 内正样本 6–93 张
- 5 个负对照（图包名零命中）：雪山 / 汽车 / 咖啡 / 鲜花 / 婴儿 —— 用来量误报

⚠️ **弱标签是噪声标签**：一个图包里必然有大量与该主题无关的图（脸部特写、换装间隙等）。
所以精确率是被**系统性低估的下界**。但同一个噪声对所有方案一视同仁，横向比较仍然成立。

### 2.3 指标

全部用**与阈值无关**的指标，避免「每个方案各自选最优阈值」这种不可比的比法
（「返回前 N 名」是所有方案共用的操作规则）：

- **P@10 / P@50 / P@100**：前 N 名里命中正样本的比例
- **R@100**：前 100 名捞回的正样本占该概念全部正样本的比例
- **零命中**：前 100 名里一个正样本都没捞到的概念个数

🔴 **语料裁剪后正样本为 0 的概念必须剔除**（`report.js` 已修）：它恒得 0 分，
却会同时压低所有方案的平均值、并白送一个「零命中」名额。子集 A 上 24 个概念都有正样本，
子集 C 上有 8 个为 0（网袜/蕾丝/死库水/绳艺/教室/停车场/猫/蛋糕），剔除后分母是 **19**。
`report.js` 现在会在输出里显式打印被剔除的清单。

### 2.4 各方案为什么能吃「同一个查询」

三种方案吃的查询形态不同，必须显式说清，否则不公平：

| 方案 | 查询形态 | 是否需要额外映射 |
|---|---|---|
| CLIP | 原始中文串（`旗袍`） | 不需要，文本塔直接编码 |
| tag 模型 | danbooru 英文标签（`china_dress`） | **需要一份 zh→标签映射表** |
| caption | 英文关键词（`china dress`） | 不需要映射表，但在描述文本里做子串匹配 |

**tag 路线的映射成本是实打实的**：现有 `search-vocabulary.js` 的 308 个词，英文侧是自然语言短语
（`a short skirt`、`a school uniform`、`stockings`），**不是** danbooru 标签（`miniskirt`、
`school_uniform`、`pantyhose`）。原样（去冠词 + 空格转下划线）能对上标签的只有 **44.8%（138/308，JoyTag）/ 48.7%（WD14）**，
而且能对上的恰好是「海滩 / 森林 / 沙漠 / 瀑布」那半——本库一张都没有。
⇒ 上 tag 路线**必须新写一份 zh→danbooru 标签表**，且它的覆盖面由 danbooru 词表决定，与图库内容无关。

## 三、成本（实测，16 核 Ryzen 7 PRO 6850H / 23.3 GB）

单张耗时在**独占 8 线程**下测得；并行跑多个任务时会因 CPU 争抢退化（实测最差退化到 4 倍），
下表给独占值。**关键纪律：`sharp.concurrency(1)` 必须设**——线上 `semantic-worker.js` 设了，
台架一开始漏了，sharp 按 16 核开自己的线程池与 ONNX 的 `intraOpNumThreads` 叠加，实测把单张拖慢 3–4 倍。

⚠️ **caption 两行（Florence-2 / BLIP）不满足「独占」这一条**：它们的耗时是当时另有台架任务在跑时测的，
含 CPU 争抢，因此 6.9 s / 4.97 s 应读作**上界**。Florence 在全 400 张的正式跑动里（3 线程、同样有并行）
均值是 **5.75 s/张**（总 2298 s），可作区间下沿参考；两数都指向同一结论（慢一个数量级）。

### 4.2 融合：tag 提精度 + CLIP 保底（24+3 = 27 个概念）

RRF（Reciprocal Rank Fusion，K=60）合并 CLIP-224 与 JoyTag 的排名：

| 方案 | P@10 | P@50 | P@100 | R@100 | 零命中 |
|---|---|---|---|---|---|
| CLIP-224 单独 | 0.181 | 0.096 | 0.070 | 0.305 | 3/27 |
| JoyTag 单独 | 0.315 | 0.195 | 0.135 | 0.478 | 6/27 |
| **RRF 融合** | 0.307 | **0.209** | **0.145** | **0.519** | **2/27** |

融合的收益不在 P@10（持平），而在两处：

1. **召回**：R@100 0.478 → 0.519，P@50 0.195 → 0.209
2. **兜底**：零返回从 6/27 降到 2/27。被 CLIP 兜住的正是 tag 词表表达不了的概念——
   空姐 R@100 0.00 → **0.18**、泳装 0.00 → **0.22**

这就是落地形态：**不是二选一，是两层**。

### 4.3 覆盖缺口（必须如实计入）

JoyTag 的 5813 个标签里**没有**可表达「空姐 / 黑丝 / 白丝」的标签
（`flight_attendant` 不存在；只有泛化的 `pantyhose` / `thighhighs`，用它查「黑丝」会把白丝也算进来）。
WD14 的 8106 个 general 标签里同样没有 `flight_attendant`，但有 `black_pantyhose` / `white_pantyhose`。

⇒ **tag 路线的表达能力上限由 danbooru 词表决定，不由图库内容决定。**
反过来 JoyTag 能表达 CLIP 表达不清的东西：`hatsune_miku`、`neon_genesis_evangelion`、
`souryuu_asuka_langley`、`zero_no_tsukaima`、`cat_ears`、`shibari` 等——30 张抽样里它直接认出了角色。

### 4.4 误报（负对照）

| 方案 | T/口径 | 雪山 | 汽车 | 咖啡 | 鲜花 | 婴儿 |
|---|---|---|---|---|---|---|
| CLIP-224 | 阈值 0.02 | 0 | 0 | 0 | 0 | 5 |
| JoyTag | T=0.5 | 1 | 0 | 1 | 5 | 0 |
| JoyTag | T=0.6 | 0 | 0 | 1 | 1 | 0 |
| JoyTag | T=0.7 | 0 | 0 | 0 | 0 | 0 |

JoyTag 的 `flower` 标签在阈值低时会误报（阈值 0.2 时 60 张），**阈值 ≥ 0.5 后基本干净**。
这是 tag 路线与 CLIP 不同的一点：它没有「基线差」那种相对化机制，误报靠绝对阈值压。

### 4.5 描述（caption）路线：子集 C 400 张上的同语料对照

描述模型的产物是「每张图一句英文」，没有向量可打分。评测做法是把查询的英文关键词在描述文本里
做子串匹配（`p.en` 逐词试），匹配上的图片作为返回集；因为描述本身没有分数，
排序用 CLIP-224 的 adjusted 分**兜底**（这一点很重要，见下）。

为可比，用同一 400 张语料重跑 CLIP 与 JoyTag（口径见 2.3；语料内正样本为 0 的 8 个概念
——网袜/蕾丝/死库水/绳艺/教室/停车场/猫/蛋糕——已从平均值与零命中分母中剔除）：

| 方案 | P@10 | P@50 | P@100 | R@100 | 零命中 | 单张成本 |
|---|---|---|---|---|---|---|
| SigLIP2-base-224（现状） | 0.295 | 0.144 | 0.104 | 0.499 | **1/19** | 0.74 s |
| JoyTag | **0.374** | **0.206** | **0.129** | **0.607** | 4/19 | 0.76 s |
| BLIP-base | 0.179 | 0.047 | 0.024 | 0.161 | 9/19 | 4.97 s |
| Florence-2-base-ft（detailed） | 0.121 | 0.038 | 0.019 | 0.127 | 13/19 | 5.75 s |

> ⚠️ **零命中分母的口径**：这里的 `4/19` 是**子集 C（400 张，剔除 8 个零正样本概念后剩 19 个）**的口径，
> 与 4.2 节表里的 `6/27`（**子集 A 1500 张、27 个概念**）**不是同一个分母**。两个数都对，
> 但分属不同语料（见 2.1 的 ⚠️），**不能互相比、也不能混着引用**；本节的结论只在这 400 张内部成立。

🔴 **两个必须同时读的口径限制**（否则这张表会被误读）：

1. **caption 的 P@N 不算它的成绩**。它的返回集大小由「描述里出现了几个查询词」决定，不由排序质量决定
   （JK制服 返回 1 张、制服 返回 4 张、丝袜 返回 38 张）。而 P@N 恒以 N 为分母 ⇒ 返回 1 张且那张是对的，
   P@10 也只有 0.1。所以对 caption 而言 **只有召回（R@100）与零命中是干净的比较轴**。
2. **BLIP / Florence 的 P@10 里有 CLIP 的功劳**。兜底排序用的是 CLIP 分，因此 0.179 / 0.121
   都是 caption 的**上界**，不是它们自己排出来的。

因此结论建立在**召回 + 零命中**两轴（与返回集大小、阈值都无关）：

| 方案 | R@100 | 相对现状 | 零命中 |
|---|---|---|---|
| SigLIP2-base-224（现状） | 0.499 | 1.00× | 1/19 |
| JoyTag | **0.607** | 1.22× | 4/19 |
| BLIP-base | 0.161 | 0.32× | 9/19 |
| Florence-2-base-ft（detailed） | 0.127 | **0.25×** | **13/19** |

**两个 caption 模型都比现状差 3–4 倍。** BLIP 自己返回集内的精确率是 P@set 0.292
（`比基尼` 一条就返回 23 张、P@set 0.609），但那是「返回得少所以精度高」，召回那一边塌了——
而这正是「搜不出来」这个用户症状的所在。

逐查询 R@100（同 400 张）：

| 查询 | 正样本 | CLIP | JoyTag | BLIP | Florence-2 |
|---|---|---|---|---|---|
| 制服 | 45 | 0.51 | **0.91** | 0.02 | 0.00 |

```

a woman in a white bikini sitting on a bed
```

主语恒为 `a woman`，服饰被压成一个颜色词（`a woman in a white dress`、`a woman in a black bodysuit`），
400 张里**一条都没出现** `uniform` / `maid` / `qipao` / `kimono` / `santa` 这类词。
Florence 的 detailed 模式话更多，语义同样平：`She is wearing a short skirt and a shirt.`

```
a woman sitting on a couch with a cat ears on her head
```

它**看见了**猫耳，却只会写成 `cat`；而用户的 `猫` 查询问的是真猫。
控制不住的词表 + 泛化的词汇，在细粒度检索里就是双向误伤。

⇒ caption 路线的价值不在「替代检索」，它是**另一类能力**（可读描述、任意自然语言问答）。
在「cosplay 图库语义搜图」这个任务上它有三处绝对短板：慢 6.7–9.3×、没有服饰/角色词表、
返回集大小不受控。**不上**。

## 五、阈值那一半问题（独立于选模型）

「关键词不准」里有两种完全不同的失败，必须分开：

1. **排序错**：`丝袜` 在阈值 0.02 下返回 1709 张、命中 0 —— 排名本身就没排对
2. **阈值卡死**：`圣诞` P@10 = **1.0**（前 10 名全对），但阈值 0.02 下**返回 0 张**
   ——用户点下去什么都没有，体感就是「不准」

全量 7374 张上的阈值扫描（27 个正样本，P@10 与阈值无关恒为 0.204）：

| 阈值 | P@set | R@set | F1 | 零返回 | 平均返回数 | 有命中的查询 |
|---|---|---|---|---|---|---|
| 0.002 | 0.083 | 0.463 | 0.140 | 0/27 | 2069 | 22/27 |
| 0.005 | 0.090 | 0.417 | 0.148 | 0/27 | 1687 | 22/27 |
| **0.01** | **0.107** | 0.341 | **0.163** | **1/27** | 1136 | **22/27** |
| 0.015 | 0.115 | 0.253 | 0.158 | 1/27 | 700 | 22/27 |
| **0.02（现状）** | 0.081 | 0.181 | 0.112 | **6/27** | 395 | **15/27** |
| 0.03 | 0.082 | 0.085 | 0.083 | 11/27 | 111 | 12/27 |

**0.02 在两个轴上都比 0.01 差**：零返回 6 个（0.01 只有 1 个），有正确结果的查询 15/27（0.01 是 22/27）。

但也不能无脑调低：0.01→0.02 这一档的**边际精确率只有约 2.8%**
（Δ命中 ÷ Δ返回 ≈ 20.8/741），往下放开等于往屏幕上灌噪声。

**正解是按每个查询自己的 top1 缩放**（自适应阈值 `score ≥ max(Tmin, α × top1)`）：

| α | Tmin | P@set | R@set | F1 | 零返回 | 平均返回数 |
|---|---|---|---|---|---|---|
| 0 | 0.01 | 0.107 | 0.341 | 0.163 | 1/27 | 1136 |
| **0.3** | **0.002** | 0.114 | 0.265 | **0.159** | **0/27** | **667** |
| 0.4 | 0.002 | 0.125 | 0.192 | 0.151 | 0/27 | 354 |
| 0.5 | 0.002 | 0.146 | 0.136 | 0.141 | 0/27 | 175 |

α=0.3 / Tmin=0.002 **拿到与最优几乎相同的 F1（0.159 vs 0.163），但零返回从 1 个变 0 个，
返回数从 1136 降到 667**（屏幕上的噪声少一半）。

## 六、被否掉的方案及理由

| 方案 | 否掉的理由 |

| **SigLIP2-base-patch16-256** | 同语料 P@10 0.188 vs 0.188、R@100 0.309 vs 0.296，逐查询互有胜负。换档要重跑全库索引 + 重标定阈值，收益为零。（原本的假说是「缩略图 256px 不会被缩到 224，省掉一次重采样」，实测这条不构成可测收益。） |

## 七、建议的落地形态

### 7.1 立刻可做（小改动）—— 阈值这一条查下来是「无需改动」

1. ✅ **结论是「无需改动」**：HEAD 里的 `DEFAULT_MATCH_THRESHOLD` 与面板那份 `MATCH_RANGE.default`
   **本来就是 `0.01`**。之前那次「改成 0.02」只存在于工作区的未提交改动里，现已完全撤回
   （`git show HEAD:src/web/js/semantic-search.js | grep MATCH_RANGE` 返回 `0.01`，
   所以那个文件现在 git 视作**未修改** —— 这也顺带证明了「0.02 从未提交」）。
   依据：全量实测 `0.01` 的 F1 0.163 > `0.02` 的 0.112，零返回 1/27 < 6/27。
   ⚠️ 注意 `settings.json` 里的**已存值优先于默认值**——用户当前存的就是 `0.01`，
   所以就算真去改默认值也只影响新装用户；已装用户要见效需点「恢复默认」。
   期间面板一度停在 `0.02` 而主进程已是 `0.01`，那段时间 `semantic-regression` **实测为红** ——
   「必须两处同改」的中间态会让整套件红。
   - 同批修了 `scripts/match-threshold-regression.js`：它把 `DEFAULT` 写成字面量 `0.02`，
     守卫跟着实现漂移、还引导人「改数字让它变绿」——改为从 `MATCH_THRESHOLD_RANGE` 派生。
2. **`MATCH_THRESHOLD_RANGE.max` 从 0.03 放开**（建议 0.15）。
   0.03 已经严到 11/27 个概念零返回、平均只返回 111 张，把一个无效档位摆在设置里没有意义。

### 7.2 建议立项（中等改动）

3. **加一层 JoyTag 标签索引**，与 CLIP 并行、用 RRF 融合。
   - 成本：单张 0.76 s（与现有 CLIP 同量级）、常驻 375 MB、存储只需标签（约 40–700 B/张）
   - 前提：**要新写一份 zh→danbooru 标签表**（现有 308 词复用率只有 45%，且复用得上的一半是本库没有的风景词）
   - 收益：P@10 1.9×、R@100 1.8×；与 CLIP 融合后零返回 6/27 → 2/27
   - 建议阈值：**T = 0.55–0.6**（0.5 开始 `flower`/`snow` 类误报抬头，0.6 基本干净）
   - ⚠️ 需要按模型词表过滤查询标签：词表无法表达的概念要显式报「不支持」，不能静默 0 结果

4. **自适应阈值**替换固定全局阈值：`score ≥ max(0.002, 0.3 × top1)`。
   依据见第五节——它在几乎不损失 F1 的前提下消灭「点下去什么都没有」。

### 7.3 暂缓

5. **GPU 加速**才是让 165 万张全库可索引的前提。当前 `onnxruntime-node` 跑的是 CPU EP，
   按实测单张成本，165 万张要 14 天以上。这件事的优先级高于任何模型选型。
   （本轮未验证 DirectML / CUDA EP 在 Windows 上的可用性，建议单独立项评估。）

### 踩过的坑（复现时别重踩）

- **`ATTACH DATABASE` 跨库挂载会被沙箱 SIGTERM**（无任何报错）。改成逐条主键查询。
- **全表 GROUP BY 扫描 165 万行 + 大 WAL 会被沙箱掐掉**。只查需要的行。
- **`sharp.concurrency(1)` 必须设**，否则 sharp 按 16 核开线程池与 ONNX 叠加，单张慢 3–4 倍。
- **caption 的排名是「集合 + CLIP 兜底顺序」**：描述文本本身没有分数，`eval-caption.js` 用
  `命中词数×100 + CLIP adjusted 分` 排序。因此它的 P@N 里混着 CLIP 的功劳，
  **不能当成 caption 的排序能力**；干净的可比轴只有召回与零命中。
- **别在另一路台架任务跑着的时候量耗时**：CPU 争抢实测能把单张拖慢到 4 倍（caption 那两行就是这么来的）。
- 🔴 **`run-tagger.js` 的 wd 分支输出失效（未修，WD14 的精度读数因此全部作废）**：
  WD-EVA02 的标签概率 **96.7% 落在 0.49–0.51**，即 logit ≈ 0 —— 模型对输入基本没有响应。
  `sigmoid(x)` 是单调的，所以这不改变**单图内**的标签序（top-20 看起来仍然「像那么回事」，
  这是最容易骗过人的地方），但**跨图比较正是评测要的东西**，而它被压平 + `toFixed(4)` 一起摧毁了：
  同一个标签在两张图上的真实差异被压到 0.501 / 0.502，排序退化成按 id 排。
  定位方向：`res[Object.keys(res)[0]]` 可能取错了输出张量（该 ONNX 有多个输出），
  或这个导出需要 RGB 而这里按 WD 惯例喂了 BGR。
  ⚠️ 判据：**跑完先看概率分布**，若大量值挤在 0.5 附近，这一路的精度结论一个都不能要。
- **语料裁剪后正样本为 0 的概念必须剔除**，否则所有方案的平均值与零命中分母一起失真（`report.js` 已修）。
- **跑长任务要 `run_in_background`**，前台会在大约 2 分钟处被 SIGTERM。
- `require('better-sqlite3')` 从 `%TEMP%` 解析会命中另一份 ABI 不匹配的包，**必须写绝对路径**。
- `import('@huggingface/transformers')` 按**脚本所在位置**解析，台架脚本必须放在项目内。
