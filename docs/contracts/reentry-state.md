# 「离开一个页面再回来，落在哪里」— 契约与取舍

> 2026-10-07 落地。守护：`ai-sidebar-regression`（桌面端行为 + 两端静态）、`ai-web-views-regression`（网页端行为）、
> `sidebar-tree-regression`（六条出口的行为 + 接线）。
> 本文只写**守护抓不到的东西**：判据为什么是这个形状、哪些写法被证伪、代价换到了什么。

## 一、搜图页结果的保留态（`retainedSearch` + `pendingRestore`）

### 用户原话与边界

> 「点击结果中的文件夹进行了跳转，重新回到搜图页面，需要保留之前的结果。」

这句话**只说了要保留**，但它隐含了反方向：从导轨的搜索图标**正常进来**时必须是干净的引导页。
两条一起才是完整的契约 —— 只做前者就会凭空冒出一屏用户没搜过的结果。

### 为什么是「一次性标记」而不是「有保留态就还原」

被证伪的两种写法，都能过掉「点目录跳走再回来」这一条：

| 写法 | 坏在哪 |
|---|---|
| 有查询 / 有保留态就还原 | 从导轨图标进来那一次也被还原 —— 用户看见自己没搜过的结果 |
| 任何一次重画都还原 | `loadPhotos()` 在扫描完成等时机也会跑（`loadSearch()`）⇒ 结果被**冻在过去**：新入库的图片永远搜不出来，**不报错、不写日志**，只能靠用户发现「怎么搜不到刚加的图片」 |

所以判据是 **「刚离开过一次」+「保留态在」+「档位与查询都同源」**。
「刚离开过一次」由 `leave()` 置位、还原时消费一次（`pendingRestore`）—— 它把
「用户离开过这一页」这个**事件**，与「页面被重画」这个**动作**区分开。后者随时会发生，前者只在用户操作时发生。

⚠️ `pendingRestore` 只允许在 `leave()` 里按保留态置位。别处直接置 true（或让 `enter()` 置真）
就退回上表第一种写法；这条有静态断言钉着（`pendingRestore\s*=\s*true` 全文件不得出现）。

### 判据只允许一份

`enter()`（决定要不要先画引导页）与 `loadSearch()`（决定还原还是重搜）**都要问同一个** `searchRestorable()`。
各写一份必然漂移成「`enter()` 画了引导页、`loadSearch()` 又还原了结果」那种一闪。

### 空结果**必须作废**保留态（唯一承重的场景）

看起来「空结果不进保留态」是句无害的好话，但它只有一个场景真的承重，而且**只有查询同源时才看得出来**：

- 查询**不同源**时，`refreshRetainedSearch()` 自己就会作废快照（它有 query / mode 比对）；
- 查询**同源**（同一个词）时，只剩这一行 `retainedSearch = null` —— 而库被重扫 / 删除之后，
  同一个词真的会从「有结果」变成「没有结果」。少了它，`leave()` 会把**当前（已经是空的）
  两组结果**刷进那份同源快照，用户回来看到的是一个「两段都空」的结果壳 ——
  看着像搜索成功过、只是没有命中。

> 这条踩过一次：第一版的回归只在「干净状态下搜一个不存在的词」上验证，
> 那时 `retainedSearch` 本来就是 null，**删掉那行也全绿** —— 假绿。
> 现在的夹具是「先搜到结果 → 把库改空 → 重搜同一个词」。

### 「干净的进入」要把查询一起清掉

只画引导页、却把查询留在 `state.aiSearchQuery` 里是最坏的组合：

1. 界面看着像没有搜索在生效，而 `enter()` 之后紧接着就是 `showTabContent` 那句
   `void loadPhotos()`（桌面端）⇒ `loadSearch()` 又拿这个词**重搜一遍**，同一页在
   「引导页 / 结果」之间来回翻；
2. 语义档更糟：**「模型尚未就绪」那段说明只在空查询分支里给**（见 `loadSearch`），
   留着查询就永远不说这句 —— 用户看到的是「搜了但没反应」。

所以 `enter()` 里 `if (!restoring) state.aiSearchQuery = '';`。
这个守卫是硬要求：**有保留态时清它，就等于「回来丢结果」**，直接违背用户诉求。
`state.aiSearchQuery = ''` 全文件只允许两处（`enter()` 的 `!restoring` 分支 + `startSearch()` 的空提交），
两处都有静态断言。

### 还原要连「更多」翻过的页与状态行一起回来

`retainedSearch` 存的是**渲染态**（folders / files / filePage / shown / status），不只是数据：

- 语义档的 `renderSearchPage(false)` 是在旧基数上「+200」。不回卷 `searchShown`（`kept.shown - SEARCH_PAGE`）
  的话，200 张会变成 300 张 —— **不报错，只是平白多画一页**。
- 状态行文案（「文件夹 N 个 · 文件 M 个」）也一起记：它是那句话唯一的载体，
  而 `setStatus()` **在节点缺失时静默 no-op** ⇒ 另存一份 `statusText` 镜像，还原时按它回写。

### 网页端必须与桌面端同口径：进 AI 视图前先 `leave()`

桌面端 `showTabContent()` 首行无条件 `aiViews.leave()`，所以**任何**页面切换都会给保留态打标记。
网页端原先只在「从 AI 视图退回浏览」时 `leave()`，AI 视图之间切换（搜图 ⇄ 人物）没有 ⇒
「从搜图去看了眼人物再回搜图」会重跑搜索（闪骨架 + 缩回第一页），而「点结果目录跳走再回来」却能保留 ——
**同一条诉求在两条路上表现不一致**。现在 `enterWebAiView()` 也是先 `leave()` 再 `enter()`。

## 二、浏览记忆（`tabMemory`）：六条出口一条都不能漏

### 症状与根因

用户原话：「每次重进文件标签页，默认跳转之前点击的文件夹」。
根因**不是记忆存错了位置**，而是它**只在两条出口上被写过**（导轨的 `.nav-tab` 点击、`viewDuplicates`）：

> 他从搜图结果点进目录 X → 之后在文件页逛到别处 → 再**从首页**进来，被带回 X。
> 首页这条出口没存过，所以记忆停在更早一次（X）。

⇒ 「重进文件页跳到**之前搜图跳转的文件夹**」这个描述本身就是诊断：跳的是**更早**那次的位置。
出口一共六条：导轨四项（搜图 / 人物 / 日期 / 重复）+ **首页** + **设置页**。

### 判据收在一处，但调用必须排在改写 `currentTab` 之前

`rememberBrowsePosition()` 按 `state.currentTab` 决定该不该存（只认 folders / dates）。
于是「什么时候调用」本身就是契约的一部分：

**排在 `state.currentTab = 'home'` 之后 = 变成空操作** —— 不报错、不写日志，
下次遇到只会看到「记忆又停在更早那次」，与本次的原始 bug 症状完全一样。
两个出口都有「调用位置必须先于切换」的静态断言。

### 存进去 ≠ 还原出来：「切 tab 归位到默认视图」那块必须让路

2026-10-07 用户报：「所有文件重新进入时为什么跳转到第一页」。

`showTabContent()` 末尾有两支「切到 folders / dates 先把右侧归位到默认视图」的重置块
（folders 那支写 `currentView = 'all'` + `page = 1` + 清路径；dates 那支反过来，只在
`currentView` 是目录视图时才归位）。它们的存在意义是**右侧不许停在别的 tab 留下的内容**，
麻烦在于它们排在 `applyBrowseTabMemory()` **之后**，且不区分这次是「套用记忆」还是「头一回进」。

folders 那支的判据是 `currentView !== 'folder' && !== 'folder_overview'` —— 而「所有文件」
的视图正是 `'all'` ⇒ **目录视图毫发无伤，只有「所有文件 / 收藏」被打回第 1 页**。
用户点名「所有文件」，就是被这条判据筛出来的。

⇒ `applyBrowseTabMemory()` 现在**回报有没有命中**，两支归位各自加 `!memoryApplied` 守卫。
判据刻意是「**记忆命中**」而不是「`fromTab` 有值」：有 `fromTab` 但记忆为空时
（设置页改完库、`invalidateTabSessionCaches()` 清过记忆），**仍然必须归位到默认视图** ——
拿旧位置硬撑是另一种 bug。

#### 三条「显式落点」不是重进，刻意不还原

同样的症状还有三条路会撞上，但它们是「去某个地方」而不是「回到某处」，保持现状：

| 路 | 走哪 | 为什么页码归 1 是对的 |
|---|---|---|
| 首页卡 / 侧栏的「所有文件」 | `viewAllPhotos()`，显式 `page = 1` | 那是这个动作本身的语义（首页卡的落点唯一性） |
| 导航历史后退 / 前进 | `applyBrowseLocation()` → `viewAllPhotos()` | `captureBrowseLocation()` 的位置键只含 `view` / `path` / `date` / `tab`，**不含页码** —— 含了会让同一个「所有文件」因页码不同算出两个位置，后退栈长出一堆假站 |
| 布局刷新引起的 `showTabContent` 重入 | 不带 `fromTab` | 没有 `fromTab` 就没有记忆可套，归位是唯一正确解 |

⚠️ **这条缝的教训比 bug 本身值钱**：上一轮的守护断言了 `tabMemory.page === 3`（**写入侧**），
没有任何一条断言「回来之后 `state.page` 是不是 3」（**还原侧**）。结果是**写入侧全绿、症状照旧**。
凡是「存了再还原」的链路，两侧都要各有一条断言；并且反方向（记忆没命中 ⇒ 必须归位）
也得有基线，否则「干脆别归位」会让还原侧那条断言假绿。

### 不在浏览页时不许覆盖记忆

在搜图 / 人物页存记忆会把 `ai_search` / `people` 这个**视图态**写进 folders 记忆
⇒ 回到相册页拿到一个 AI 视图。`viewDuplicates` 的注释专门讲过这一条，
所以判据刻意**不是**「`currentTab !== 'folders'` 就宽泛地记一笔」，而是窄判据
（`currentTab === 'folders' || 'dates'`）。

### 「跳转过去也算浏览记忆」（用户拍板，别回退）

一种看起来更「干净」的方案是：从搜图结果跳进目录时**不记**这一跳，
让文件页的记忆只保留「用户自己逛出来的位置」。用户明确否掉了这个方向：
**「跳转过去也算浏览记忆」**、要的是**「记住之前退出时的位置」**。

⇒ 语义保持「离开文件页时的位置，就是记忆」，本次只补上漏掉的出口，不改判定语义。
配套：`saveBrowseTabMemory(...)` 的调用点在全文件只该有四处
（定义 1 + `rememberBrowsePosition` 1 + `viewDuplicates` 2），多出来的调用点意味着有人绕过了统一判据。

## 三、验收方式（这两个契约的共同点）

两半都是**页面态**契约，静态检查抓不到「用户回来看到什么」。可用的探针形状：

- **行为面**：假 DOM 驱动真实适配层（`ai-sidebar-regression` / `ai-web-views-regression`），
  断言「回来的那一屏内容逐条一致」+「没有多发一次请求」+「没有闪骨架」；
  两个方向都要有基线 —— 「离开过 ⇒ 不重跑」必须配一条「没离开过 ⇒ 重跑」，否则
  「还原」与「把结果冻住」在断言上长得一模一样。
- **接线面**：`rememberBrowsePosition()` 这类「判据收在一处」的辅助函数，
  出口的**调用位置**也是契约 ⇒ 必须同时断言「调了」和「调在切换之前」。
- 两半都有「看起来删掉也没事、其实只在某个特定顺序下承重」的行（空结果作废、放置顺序）。
  **给这类行写牙时，夹具必须走到那个特定顺序**，否则就是假绿。
- **最后一公里别忘在网页端**：这次的修复落在 `src/web/js/app.js` 与 `src/web/js/ai-views.js`，
  两个都是 `sw.js#SHELL_ASSETS` 里的资源 ⇒ 必须同批抬 `CACHE_NAME`（并同步 `index.html` 的 `?v=`）。
  不抬的话**静态守护全绿、线上永远拿不到改动**（cache-first）。这一类的判据只有两条：
  ① 清单每条与 `index.html` / `manifest.webmanifest` 的引用逐字相同（含 `?v=`，`caches.match`
  按完整 URL 做键 —— 少一个 `?v=` 那条预缓存就是死条目，首屏离线时缺文件），由
  `web-asset-route-regression` 第 ⑦ 组钉住；② 「改了清单里的资源有没有抬版本号」**静态判不了**
  （没有内容清单可比对），只能靠改动时的人工纪律 + 真装一次 PWA 看。
