# 后台任务对前台操作的影响 —— 实测诊断

> 需求来源：「后台任务执行时，需要保证软件本身的各项操作正常运行。」
> 诊断日期：2026-10-06 · 状态：**只出报告，代码未改动**
> 让路强度口径（用户已选定）：**降到并发 1**，不采用「完全暂停」。

---

## 0. 结论速览

| 怀疑对象 | 实测结论 | 依据 |
| --- | --- | --- |
| 主进程 event loop 被同步代码阻塞 | ❌ **不是主因** | 每行连续同步段典型 **<1 ms**，p99 ≈ 23 ms |
| `dbWriteQueue` 写锁把前台操作堵住 | ❌ **不是主因** | 前台的收藏 / 删除**不过写队列** |
| CPU 被 sharp 解码抢光 | ⚠️ **次要**（等效 2.4 核 / 16 核） | 时间主要花在 I/O 等待，不是算 |
| **外接盘 I/O 争用** | ✅ **真瓶颈** | 冷读一张 20 MB 照片 **929 ms**，而等效 CPU 只占 **0.26 核** |
| **前台保护机制本身** | ✅ **真正的问题** | 唯一接线的只有「搜图抢占」，另三处**断线或不存在** |

**一句话**：后台任务对主进程的「计算干扰」比直觉小得多；真正的问题是**前台状态压根没告诉后台**
——降载手段完全现成，只是没人触发。

## 2. 逐项实测

### 2.1 SHA-256：主进程唯一的纯同步重计算

`main.js#processOne` 里 `hashBufferSha256(sharedBuf)` 是**纯同步**的
（`src/main/file-hash.js: crypto.createHash('sha256').update(buf).digest('hex')`），
对 ≤64 MB 的文件**整份在内存里算**，期间主进程 event loop 完全不响应。

| 字节量 | 中位耗时 | 最快 | 最慢 | 吞吐 |
| --- | --- | --- | --- | --- |
| 0.5 MB | 0.30 ms | 0.29 | 0.35 | 1665 MB/s |
| 2 MB | 1.14 ms | 1.09 | 1.19 | 1751 MB/s |
| 8 MB | 4.44 ms | 4.15 | 4.57 | 1802 MB/s |
| 18 MB | 9.75 ms | 9.10 | 10.38 | 1846 MB/s |
| 40 MB | 21.87 ms | 21.01 | 23.23 | 1829 MB/s |
| 64 MB | 37.03 ms | 35.00 | 38.84 | 1729 MB/s |

**这台 CPU 有 SHA-NI 硬件加速（约 1.8 GB/s）**，所以 18 MB 只要 9.75 ms。
在没有该指令集的老机器上会慢 3-5 倍，届时这个结论需要重新量。

### 2.2 每行「连续同步段」有多长

模拟真实序列 `updatePhotoDhash(18 参数) → SHA-256 → updatePhotoHash`，**中间没有 await**：

| 字节量 | 每行耗时 |
| --- | --- |
| 0.5 MB | 0.39 ms |
| 2 MB | 1.18 ms |
| 8 MB | 4.71 ms |
| 18 MB | 10.51 ms |
| 40 MB | 22.55 ms |
| 64 MB | 35.73 ms |

**映射到真实库**（`file_size` 沿 id 抽样 1672 行）：

| 分位 | 字节量 | 推算的单行同步阻塞 |
| --- | --- | --- |
| p50 | 4.25 MB | **约 3 ms** |
| p90 | 15.05 MB | **约 9 ms** |
| p99 | 40.45 MB | **约 23 ms** |
| p99.9 | 678 MB | 走流式异步，**不阻塞** |

字节量分布：`≤2MB 27.2% · 2-8MB 44.5% · 8-18MB 22.2% · 18-40MB 5.0% · 40-64MB 0.5% · >64MB 0.5%`

**判读**：16 ms 是一帧。典型情况（p50-p90）**低于一帧**，用户感知不到；
只有 p99 那一档会偶尔掉一帧。**而且只有缺 `file_hash` 的行才走这段**
（抽样中 1649 张里 324 张，约 20%）。

> ⚠️ 超过 `THUMB_SHARED_READ_MAX_BYTES`（64 MB）的文件走流式 `hashFileSha256`
> （异步、有背压、可取消）⇒ 库里那些 600 MB+ 的视频/大图**不会**阻塞主进程。

### 2.3 单条缩略图 BLOB 写入

| BLOB 大小 | 中位 | 最坏 |
| --- | --- | --- |
| 10 KB | 0.103 ms | 0.360 ms |
| 25 KB | 0.167 ms | 0.403 ms |
| 50 KB | 0.162 ms | **15.226 ms** |

中位可忽略，但**最坏出现 15 ms 的偶发尖峰**——量级与一次 WAL 维护 / fsync 相当。
（当前 `photos.db-wal` 有约 1.29 GB 未合并，这个尖峰值得后续单独观察。）

### 2.4 写锁：前台写操作**不走队列**

`dbWriteQueue.run(` 在 `main.js` 里共 11 处，**全部是后台任务**
（scan / thumbnail-backfill / dup-hash / invalid-cleanup / 启动索引）。
前台的 `photo-toggle-favorite`、`photo-move-to-trash`、`photo-delete-record`
直接调 `db.*` 同步执行，**不入队、不等锁**。

而 better-sqlite3 是同步 API，`db.transaction(fn)` 执行期间 event loop 不会切换
⇒ 前台写**不可能**插进后台事务中间，也就不存在「等一批 100 行写完」的问题。

**结论：写锁不会饿死前台操作。**

### 2.5 CPU：不是主要争用

以真实照片（3 并发、含 20-30 MB 大图）解码 256px 缩略图，测「进程 CPU 时间 ÷ 墙钟时间」：

| `sharp.concurrency` | 墙钟 | CPU 时间 | **等效占用** | 每张 | 相对吞吐 |
| --- | --- | --- | --- | --- | --- |
| **未设（现状）** | 14859 ms | 3812 ms | **0.26 核** ⚠️ | 929 ms | — |
| 4 | 1509 ms | 3625 ms | 2.40 核 | 94 ms | 985% |
| 2 | 1671 ms | 3828 ms | 2.29 核 | 104 ms | 889% |
| 1 | 2146 ms | 3562 ms | 1.66 核 | 134 ms | 692% |

> ⚠️ **「未设」那一行是被污染的**：它是第一轮，文件还在外接盘冷缓存里；
> 后面三档都是热读。10 倍的墙钟差**几乎全部来自磁盘 I/O**，不是 CPU。
> 这行数据的价值恰恰在于它暴露了真瓶颈——**等效只占 0.26 核，却花了 929 ms/张**。

**判读**：
- 三种 `concurrency` 设置下等效占用都在 1.66-2.40 核，16 核里**占比不高**
- 限制到 `concurrency(1)` 的代价是吞吐降到 **69%**（134 ms vs 94 ms）
- ⇒ 单靠限制 `sharp.concurrency` 收益有限；**外接盘 I/O 才是要被让路的资源**

## 3. 真正的缺口：前台保护机制断线且覆盖极窄

| 机制 | 代码位置 | 状态 | 证据 |
| --- | --- | --- | --- |
| 搜图**抢占**（停批次） | `interaction-preempt.js` + `main.js:2727/3119/3127/5954/5983` + `web-server.js:552/2934` | ✅ 真接线 | 桌面 + 网页搜图都包了 `withPreempt` |
| 视频播放**降载** | `previewPlaybackActive`（`main.js:647/2157/2905/3459/4927`） | ❌ **零调用** | 全局 grep：只有 `preload.js:281` 与 `renderer/api.js:247` 两处**定义**，无任何调用点 |
| 静态大图预览 | —— | ❌ **信号不存在** | 渲染层只有 `isPreviewVideoPhoto()`，没有静态图的上报 |
| 翻页 / 切目录 / 人物页 | —— | ❌ 无信号 | `withPreempt` 仅包裹搜图 |

### 这个缺口为什么重要
- **降载手段是现成的**：`getEffectiveThumbBackfillConcurrency()`
  （`main.js:2156`）在 `previewPlaybackActive` 为真时返回 **1**，否则返回用户设置值（默认 3）。
  也就是说，**只要有人把信号置位，缩略图补全与查重的并发立刻从 3 降到 1，
  外接盘争用直接降 2/3**——代码不用改一行。
- 视频播放走 HLS（`/api/video-playback` → `web-server.js` → ffmpeg 转码），
  **转码本身是重度 CPU 操作**；播放期间后台不但没降载，还在一起抢 CPU 与磁盘。
- 双击打开一张 30 MB 大图时，后台正以 3 并发读同一块盘 ⇒ 大图加载变慢。

> 这与本项目已经踩过的另一个坑同型：`api.notifyBrowseUiReady` **零调用**
> ⇒「画完目录树再跑启动任务」从未生效，永远走 12 s 兜底。
> **定义了 API、主进程也接了，唯独渲染层没人调** —— 这类失效不报错、不写日志、
> 静态守护也全绿，只有真跑一遍才看得见。

## 4. 建议的改造方案（待实施）

### 方案 A（推荐 · 已选定让路强度）
**把「用户正在看图 / 看视频」接成前台活动信号，复用现成降载。**

1. **接上断线**：在预览打开/关闭（含视频播放/暂停）处调用
   `api.notifyPreviewPlaybackActive(true/false)`（`src/preload.js:281` 已就绪）。
2. **扩大触发面到静态大图**：双击打开预览、幻灯片播放时同样置位
   —— 复用同一通道，语义从「播放中」泛化为「正在查看」。
3. **让路强度 = 降到并发 1**（用户已选定）：任务**照跑不停**，只是并发 3 → 1。
   这正好是 `previewPlaybackActive` 现有的设计语义（`interaction-preempt.js:28-35`
   明确区分「降载」与「抢占」，不要合并）。
4. 关闭预览即恢复（`false`）。

**预期效果**：看图/看视频时，外接盘争用降 2/3；补全速度下降但不停摆。

**必须做的配套**（否则会重蹈覆辙）：
- 加**行为面守护**：断言「预览打开 → `getEffectiveThumbBackfillConcurrency()` 返回 1」，
  以及「渲染层真的有调用点」（不是只断言 API 存在——那正是断线能全绿的原因）。
- 该信号是**布尔量且会泄漏**（用户直接关窗口 ⇒ 永远 true ⇒ 后台永久降到 1）。
  建议照 `interaction-preempt.js` 的三条防线处理：**计数而非布尔 + try/finally 收尾 +
  自动过期尾巴**，不要新写一个裸布尔。

### 方案 B（未选）· 再加上翻页 / 切目录
覆盖面更全，但翻页是**高频短操作**：每次翻页都降载，会让补全被反复打断，
整体推进显著变慢。若要做，建议改走 `interactionPreempt` 的**短抢占**（带 `tailMs` 尾巴）
而不是降载，且必须实测对补全吞吐的影响再决定。

### 方案 C（可选）· 主进程 sharp 并发
`face-worker.js:9` / `semantic-worker.js:18` 都显式写了 `sharp.concurrency(1)`，
**唯独主进程一处没设**，libvips 默认开 `os.cpus().length`（本机 16）个线程。
实测限制到 1 只把等效占用从 2.40 降到 1.66 核、吞吐降 31%
⇒ 因 I/O 主导，**收益有限**，优先级低于方案 A。
