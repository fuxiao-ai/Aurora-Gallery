# 本地 AI、多语言搜图

实现日期：2026-09-25。模型与索引在图库主机运行，桌面和授权 Web 客户端共用检索服务。没有接入云端推理、在线翻译或照片上传。

## 使用

1. 重启桌面应用，点左侧导轨的「搜图」进入 AI 搜图页。
2. 进入「设置 → AI 与索引 → 搜图索引」，点击「下载 / 修复模型」。首次联网下载约 412 MB 文件（十进制；主要为 283 MB 文本模型、95 MB 视觉模型、34 MB tokenizer），随后本地加载并验证两种编码器。失败会显示错误，可以重试；缓存文件会复用。**安装包若已随包内置模型（见「随包内置模型」一节），这一步会被跳过**：打开搜图页时就把随包的那一份播种进用户目录，按钮直接显示已就绪。
3. 点击「建立 / 更新索引」。处理已扫描入库的静态照片，优先使用缩略图。新增或文件元数据发生变化的照片会重新编码，未改变的条目跳过。可停止任务，已完成条目保留，下次继续更新。
4. 回到「搜图」页的左侧栏搜索框，输入「一只猫」「一场足球比赛」「a cat」「a football match」等描述。支持模型覆盖的多种语言，效果因语言与内容而异，不保证所有语言同等准确。
5. 返回**所有达到匹配阈值的照片**（按相似度排序），点击进入现有预览。阈值默认 `0.01`，可在「设置 → AI 与索引 → 搜图索引」的「匹配阈值」一栏里调整（`0` 等于不过滤，越大越严）。搜索覆盖整个已索引图库，不继承普通浏览页的目录、日期、收藏或媒体筛选。

搜索框下方常驻一组**预选词**：每次进入搜图页，从主进程给回的**词池**里洗牌抽 5 个（同批不重复），点一下即回填输入框并直接开搜；右侧「换一批」可手动重抽——「换一批」只是**再洗一次牌**，不会重跑模型。它只是起点提示——不进搜索历史。抽样结果只在「进入搜图页」与「换一批」两个时机更新，状态轮询或语言切换引起的重绘不会让词跳变。主区引导页那 5 个示例词是固定的，与侧栏随机词互不影响。

这一块有**三种形态**，由取词状态决定：**词池就绪** → 摆真词；**正在取** → 摆 5 个骨架 pill（标题右侧「换一批」让位给「挑选中…」，容器挂 `aria-busy`）；**取不到**（没索引 / 模型没就绪 / 任务忙 / 一个词都不达标 / 本会话已失败过）→ **整块收起**，连标题一起，不摆空壳也不摆假词。骨架**不是装饰**：取词要起一个只读 worker（载模型 ~2.1s）+ 打开索引（~0.7s）+ 打分（~1s），冷启还要现算 308 个词的词表向量（~15s），而**这些时间每次进页面都要付一遍**（只读请求每次新起 worker）。旧实现在这整段等待里把这一块 `hidden`——摆 18 个硬编码词时渲染是瞬时的，所以那个空窗是换词源之后才出现的观感回退：用户读到的不是「正在算」而是「没有」。⚠️ **失败分支必须重画**：只改状态不重绘会让骨架**永久停在「挑选中…」**，加载态假死比空白更糟（`ai-sidebar-regression` / `ai-web-views-regression` 各有一条断言专门钉这个）。骨架的底色用 `--bg-hover`（它在每套主题里都有定义、相对本层底色总是同向偏一档；`--bg-card` 在浅色下是纯白、`--text-muted` 混色在深色下几乎与背景同色，两档都试过不行），并尊重 `prefers-reduced-motion: reduce`。

**词源在服务端**（`src/ai/search-vocabulary.js`）：308 个词、分十类（自然风光 / 天气季节 / 城市建筑 / 人物生活 / 服饰造型 / 题材风格 / 美食 / 动物 / 物件 / 室内 / 色调节日），每个词写成 `[中文, 英文]` 一对。进入搜图页时，整份词表一次性交给主进程，按**与检索完全同一套口径**（基线差 + 当前阈值）在本库上跑一遍，**按真实命中数排序**取前 24 个组成词池（`SUGGEST_POOL_LIMIT`），一个会话只跑一次。所以「点下去有图」是**算出来的**，不是猜的。

为什么要换词源：原来词库是界面里写死的 18 个通用风景词，再用「这些词在库里有没有内容」筛一遍，而筛不出结果时**回退整份静态词库**。本机库以动漫 / cosplay 图包为主，18 个词里 13 个是 0 张，点下去什么都没有——根子不在筛选，在**词源太窄**：库里根本没有「夕阳下的海滩」这种东西。现在词表宽到「任何一类图库都能被命中几个」（服饰造型与题材风格这两类就是为动漫 / cosplay 库补的：泳装、制服、双马尾、银发、棚拍、逆光、黑白照片…），显示哪几个词则完全由这个库的实际命中数决定。

词源仍然**是人写的**，不是从图库里长出来的：SigLIP2 是双编码器（文本塔 + 图像塔），没有解码器，从入库的图像向量里吐不出任何一个词；要真从图里生词必须再挂一个 caption 模型（BLIP-2 / LLaVA 那类），那是另一套模型、另一份内存、另一段索引时间。所以这里取的是「**够宽的人写词表 + 数据驱动的筛选与排序**」——词表够宽保证有词可挑，挑哪些词交给数据。

拿不到词池时（没有可用索引 / 模型未就绪 / 任务忙 / 一个词都不达标）**不回退到任何静态词库**：旧实现正是在这里回退，于是库里一个都没有的「夕阳下的海滩」照样被摆出来给用户点。宁可把这一整块**隐藏**（连标题和「换一批」一起收起来），也不摆已知没结果的词。引导页那 5 个示例词是唯一的例外：它们**只在词池为空时**兜底（否则引导页会是一片空白），因此文案上写的是「示例」而不是「你库里有的」。

**命中 0 的词一律不返回**（服务端 `DEFAULT_MIN_HITS = 1`）：预选词存在的意义就是「点下去有图」。门限卡在 **1** 而不是 2：要挡住的是「0 张」那一种（点下去空手而归），而「命中 1 张」点下去照样有图可看，与 0 张是两个世界。曾按「不让只有一张图碰巧沾边的词混进来」定成 2，在同一次实测里被否掉——那个库以人像为主，达标的词本来就少，卡 2 会把侧栏从 5 条缩到 3 条，为一个想象中的噪声问题牺牲一半位置；何况抽样本身就有噪声，命中 1 与 2 的差别在噪声范围内。

Web 端仅提供状态和查询，下载、索引及停止由桌面端管理。远程浏览器的查询发送给自己的图库主机处理；请求仍经过现有访问控制。**搜索在索引构建期间照常可用**，结果只覆盖已落库的那部分向量；索引仍在建立时，界面会写明「仅基于已索引 N 张」。普通浏览可以继续。

## 索引进行中搜索（为什么是「托付」而不是「另起一个 Worker」）

整库索引可能跑上数天，期间不能把搜索锁死。**搜图索引**在跑时，搜索只能托付给同一个 Worker：

- 索引 Worker 正在跑时，搜索请求通过 `relayReads` 投递给**同一个 Worker**，复用它已经载入的编码器与图库连接；索引循环每张照片都让出事件循环，因此搜索能插进来，代价是索引短暂停顿。任务状态、进度不被顶替，索引不被打断。
- **不要改成「另起一个 Worker」**：真正的约束是**并发两份 SigLIP2**，而根子是**内存**。实测（`%TEMP%` 下的 `xconc` 诊断，`ELECTRON_RUN_AS_NODE` 模式）——搜图索引 worker 在跑时再起一个 worker 载第二份 SigLIP2，进程在「准备载第二份」的瞬间静默死亡，死前记录的可用物理内存只剩 5 MB。所以死因不是「两份 ONNX 会话」本身：YuNet+SFace 载两份一直相安无事。**这条路在代码上绕不过去**——只要有 Worker 在跑，`primary` 就为 false，必然走 relay。
- **人脸索引在跑时，搜图照常可用**（原先的 `canSearch` 闸门已撤除）。那种场景没有 Worker 可托付，只能自己起一个搜图 Worker；它是安全的，因为搜图 Worker 现在**只载文本编码器**（`loadEncoder(..., { textOnly: true })`），实测常驻内存从约 1170 MB 降到约 900 MB（省约 270 MB，两次实测 276 / 269 MB，见 `scripts/semantic-encoder-memory-smoke.js`）。两个索引之间仍互斥（`canRun`），理由是各占一套模型、抢着读 `photos.db`，不划算。
- 索引刚好结束时的迟到请求由 Worker 直接回 `AI_BUSY`，调用方重搜一次即可，不会误当成一次主任务。

**与数据库维护互斥（两个方向都要拦）**：索引 Worker 在整段索引期间一直持有 `photos.db` 连接并反复写批次事务，此时做 `VACUUM` / 重建缩略图标记必然抢不到写锁，实测报出来的就是 `database is locked`（维护 Worker 等满 8 秒仍然失败）。因此：

- 维护方向：`maintenanceBusy()` 把「任一 AI 索引在跑」算作忙碌（`src/main/maintenance-guard.js` 的 `aiIndexBusy`），从「设置 → 后台任务」点优化时直接拒绝并提示「后台任务进行中」。只读查询（搜图 / 人物列表）走的是不写任务状态的并发分支，**不会**被算成忙碌——所以在搜图索引跑着的时候，你还是一样能搜、能看人物，只是不能点数据库维护。
- 索引方向：`canRun` 在数据库维护期间返回错误码 `AI_MAINTENANCE`，界面提示「数据库维护进行中，请稍后再试」——刻意与「另一套 AI 索引在跑」（`AI_BUSY`，提示「AI 任务正在运行」）区分开，让用户知道到底该等谁。

维护侧还会在动手前算一次 VACUUM 的空间账（同样在 `maintenance-guard.js`）：需要额外 `库内可回收后的大小 × 1.15 + 64 MB` 的临时空间，数据库所在分区与系统临时目录**两处都要够**，不够就直接拒绝而不是跑到一半 I/O 失败；确认弹窗里同时给出「本次需要额外约 X」与「库内可回收约 Y」，避免为了几 MB 空洞去重写整库。

> 复现这批结论的脚本是一次性诊断（不在仓库里），要点：借用真实模型目录只能用 **junction**，且收尾必须**先摘掉 junction、确认整棵树再无链接**，才允许 `rmSync(recursive)`——Node 在 Windows 上会顺着 junction 删掉**目标**里的真实模型文件。仓库里那几个 `*-smoke.js` 已经按这个顺序写好了。

## 模型与索引

下载和索引任务接入统一后台任务面板，支持跨页面查看、折叠、停止及跳转设置。索引展示完成、失败、跳过数量、当前文件及平均处理速度；下载显示当前文件百分比。索引不预先统计整库，不显示总百分比和预计剩余时间。停止保留已完成结果，后续增量继续。普通查询及查询时的模型加载不会显示为索引任务。

- 使用 [SigLIP 2 base patch16 224 ONNX](https://huggingface.co/onnx-community/siglip2-base-patch16-224-ONNX)，固定 revision `ba1f3b0`，文本和图像均为 q8。
- 模型家族说明：[Google SigLIP 2](https://huggingface.co/google/siglip2-base-patch16-224)。接入依据：[Transformers.js 3.8.1 SigLIP 模型 API](https://huggingface.co/docs/transformers.js/v3.8.1/api/models#module_models.SiglipTextModel)。新增依赖固定为 `@huggingface/transformers@3.8.1`。
- `src/ai/embedding.js` 实现图文编码与 768 维归一化。只有显式安装操作允许联网，其余加载设置 `local_files_only: true` 和 `allowRemoteModels: false`。
- `src/ai/index-store.js` 使用图库数据库的只读连接，将向量写入旁路 SQLite。有效性由照片 ID、路径、大小、修改时间和模型版本共同判断，已删除或已变化的条目不会出现在结果中。
- 数据位于应用用户数据目录下的 `ai-search/models`、`ai-search/ready.json`、`ai-search/semantic-index.sqlite`。原图库表不迁移，原照片不修改。
- 每批最多 16 张照片，检索每批最多 256 条向量。所有 SQL、图片处理和 ONNX 推理均在专用 Worker 中，限制 ONNX CPU 线程和 Sharp 并发。重活（下载模型 / 建索引）一次只允许一个，Worker 退出后才能接收下一项任务；只读搜索是唯一例外——搜图索引进行中由同一个 Worker 顺带服务（见上一节）。
- 搜图只载文本编码器（`textOnly`），建索引与下载才载视觉编码器，因此单次搜索的常驻内存明显更低；代价是搜索不能编码图片，只能做文本召回。
- 当前按「基线差 + 阈值」遍历全部有效向量（见下节），**不再是「取前 60 条」**。内部为内存起见最多保留最相近的 5000 条（`MAX_RESULTS`）——阈值调到 0 时「一张照片」这类泛化查询能命中全库的一大半，百万库里上百万个行对象同时驻留是崩溃而不是功能。因此 `matched`（达标总数）与 `photos`（实际返回）是两个数，截断时另用 `truncated` 标记，界面按 `matched` 显示。百万条索引的向量本体约 3.1 GB，尚未采用近似最近邻索引；不能据此承诺百万图秒级响应。搜索超时为 120 秒。
- 每项操作结束后释放模型与 Worker，节省闲置内存；下一次查询需要重新加载本地模型。停止在可取消下载或图片/批次边界响应，不能保证正在进行的原生推理立即中断。

### 随包内置模型（`models/`，免去首次下载）

安装包可以自带这套模型，用户就不必先点一次「下载 / 修复模型」：

- 仓库根的 `models/` 由 `npm run bundle-models` 生成（`scripts/bundle-models.js`）：`models/search/` 是 Hugging Face 缓存的原样目录（`onnx-community/siglip2-base-patch16-224-ONNX/ba1f3b0/…`，实测量级 393 MiB / 约 412 MB 十进制），`models/face/` 是人脸那套（约 13 MiB），另加 `models/manifest.json`（每个文件的 size + sha256，以及搜图这一份的 `modelKey`）。该目录**不进版本库**（`.gitignore` 的 `/models/`），打包时由 `scripts/after-pack.js` 整体复制进 `resources/models`。
- 运行时由 `src/ai/bundled-models.js` 播种到用户目录：`models/search` → `ai-search/models`（并写 `ready.json`）、`models/face` → `face-index/models`。入口挂在 `SemanticSearch.refresh()` 的 `beforeRefresh` 钩子上（`src/main.js` 给两个服务都挂上），所以**桌面端与网页端谁先打开 AI 视图谁触发**，且每进程只做一次（memo）；已就绪时只剩一次 `statSync`，不重复搬文件。
- 三道闸门，缺一不可：① `manifest.search.modelKey` 必须与当前 `MODEL_KEY`（含 revision 与量化档）逐字符相同 —— **对不上就一个字节都不复制、不写 `ready.json`**，宁可让用户走下载，也不能把上一代权重标成当前这一代；② 复制完按 manifest 的 sha256 全量核对 —— 播种没有「真载一遍编码器」的机会（那正是安装流程落 `ready.json` 前的验证），哈希不符就停在 `hash-mismatch`、不落标记；③ 人脸一侧不看 manifest，判定权归 face worker 的 `verify()`，播种只做「缺了才补、尺寸不对才换」。
- 播种**只报不抛**：任何异常都降级成原来的「点按钮下载」，不会变成新的启动故障点。`scripts/bundled-models-regression.js`（已进 `run-regressions.js`）用几 KB 的夹具钉住上面这些判定（幂等不重写、尺寸修复、`model-mismatch` 不落标记、`hash-mismatch` 不落标记、没有 manifest 不播种、一侧坏掉不拖垮另一侧），另有静态断言守住「钩子还挂着、afterPack 还复制 `resources/models`、`.gitignore` 还忽略 `/models/`」。本机用真实 `models/` 播种到临时用户目录时，`face verify()` 为真、`ready.json` 与 `MODEL_KEY` 一致，再播一次报告 `already-complete` / `already-ready`（`copied: 0`）。

## 匹配阈值：为什么用「基线差」而不是原始余弦

决定「哪些照片算搜到了」的分数是**基线差**：

```
score = sim(查询, 图片) − sim(泛化文本, 图片)      # 泛化文本固定为「一张照片 a photo」
```

先算查询与照片的相似度，再减掉**这张照片与一句泛化文本**的相似度（与 `install` 阶段验证编码器用的是同一句，见 `embedding.js` 的 `GENERIC_TEXT`），剩下的才是这个查询自己带来的信号。

为什么要绕这一下：SigLIP 的余弦值整体偏高，且**每张照片都有自己的底噪**——一张照片即使与查询毫无关系，余弦也常在 0.05–0.1 之间。四种候选口径都在真实库上实测过（约 7400 条已索引向量）：

- **原始余弦 + 固定阈值**：库里没有的乱码查询在 `0.08` 上仍有 3027 张「达标」，比真有内容的「美食特写」（673 张）还多，根本分不开。
- **相对全库均值的 z 值**：库里没有的「汽车」top1 z=5.73，库里真有的「女孩坐在室内」只有 2.31——反了。
- **衰减率**（第 60 名 / 第 1 名）：真有的「人物肖像」0.91，没有的「汽车」0.73——也反了。
- **基线差**（采用）：库里没有的概念与乱码一律 0–1 张，库里真有的概念能到几十上百张。

最后一组用本机真实库（7374 条向量）复核过，可复现：

- 库里真有的「人物肖像」在阈值 `0.01` 下命中 **84** 张、`0.005` 下 358 张、`0.02` 下 1 张；
- 库里没有的「汽车」**0** 张、「夕阳下的海滩」**0** 张，乱码「嘎嘎嘎 噜噜噜」**1** 张；
- 旧的那份 18 词静态预选词里 **13 个是 0 张**——那个库以人像 / cosplay 为主，「雪山和湖泊」
  「美食特写」「秋天的落叶」是**真的没有内容**，不是搜索坏了。这一条正是后来换词源的直接依据。

阈值定在 `0.01` 时这两类首次稳定分开；不能往下放：`0.005` 时乱码能拿到 6 张，与真有内容的
「美食特写」同量级。这顺带解释了改之前那个困惑——原始余弦下「美食特写」看着有 673 张
「达标」，其实一张都不是美食照，**它衡量的从来不是「有没有」，而是「像不像」。**

因此状态行写的是「**N 张达到匹配阈值**」而不是「找到 N 张照片」：它回答的是「有多少张越过了你设的线」，不是「这些就是相关的」。

**阈值定义在一处**：`src/ai/index-store.js` 的 `MATCH_THRESHOLD_RANGE`（范围 `[0, 0.03]`、默认 `0.01`），主进程的设置默认值与越界夹取都从它取。设置里的输入框在 `src/web/js/semantic-search.js`（桌面嵌板 / 桌面整页 / 网页弹窗共用同一份文件），渲染层拿不到主进程模块，所以那里另有一份 `MATCH_RANGE` 常量，**回归会断言两处数值逐一相等**。上限 `0.03` 已经严到多数查询直接返空（实测「人物肖像」在 0.02 时只剩 1 张）。

**输入框的几条约定**：用输入框而不是滑杆，是因为有效区间只有 `[0, 0.03]`，滑杆上能对齐的有意义取值就那几档，拖拽精度还不如直接敲数字，而且滑杆没法表达「清空 = 回到默认」。框里**开箱就带着默认值**（读到真值之前也不是空的），另有「恢复默认」按钮。文本到阈值的换算有四条反直觉但要紧的规则：

- **空框不是 0**。`0` 是有意义的一档（不过滤），所以清空输入框不能被顺手当成「把所有照片都返回」——空与非法输入一律回落到默认值 `0.01`；
- **越界不报错，直接夹回范围**：`1` 变成 `0.03`，`-5` 变成 `0`；
- **框里显示的永远等于真正生效的值**：`1` 提交后会立刻在框里回写成 `0.03`，否则「填了 1」会留在框里造成已经生效的假象；
- **写回失败要回滚显示并报错**（乐观更新 + 失败回滚，与人物改名同一套写法），不能静默吞掉。

这几条由 `scripts/match-threshold-regression.js` 逐条覆盖（含「迟到的读取不许覆盖用户刚填的值」）。

**基线存在索引里**（`embeddings.generic_sim`），不随查询变。老索引**不需要重建**（百万库重建一次是数天）：新增列后历史行为 NULL，检索时按需补算并写回，攒够 20000 条落一次库、写失败就整批丢弃下轮补上；新行在建索引时顺手算好。检索时**入库值优先于调用方传进来的 `baseline`**，后者只用于给老行补算——否则同一批数据会因为「这次有没有传 baseline」给出不同结果。

预选词打分的抽样（`index-store.js` 的 `scoreCandidates`）**以 `MIN(photo_id)` 为锚点，在 `[lo, hi]` 上等距铺 8 段窗口**，每段读 `sampleSize / 8` 条；库小到 `COUNT(*) <= sampleSize`（默认 3000）时**直接全量扫**——几千条向量不值一提，而且全量扫让小库的取样误差归零、回归断言可以精确复现。窗口之间会重叠（库小时几乎必然），所以按 `photo_id` 去重——同一张照片重复计分既浪费又会让命中数变成「命中次数」而不是「命中张数」。

**锚点必须是 `lo`，取样必须是确定性的**，这两条都是修 bug 修出来的：

- 原来的起点是 `1 + random × (hi − 1)`，取的是**整个 id 空间** `[1, maxId]`；而本机那份索引的向量只落在 `324737..332328` 这一段窄带里。于是约 98% 的随机起点落在带**之前**，`WHERE photo_id >= start LIMIT 500` 每次都返回**同一批最早的 500 行**——`sampled` 恒为 500/7374 = 6.8%，而且每次结果一模一样。改成从 `lo` 起等距铺开之后，同一份 7374 条的库上 `sampled` 稳定为 **3000**（= `sampleSize` 上限，8 段 × 375 条），命中数也从「只看到最早那 500 张」变成覆盖全库 40.7% 的均匀取样。
- 抽样**不许有随机**：随机取样会让同一份库两次进入搜图页给出不同的预选词、不同的 `sampled`，既不可复现也没法写断言。回归里有一条差分断言专门钉这个：把锚点换回 `1 + random × (hi − windowSize)` 必须让断言 FAIL。

## 已知范围

- 只索引静态照片，不分析视频帧。RAW 优先使用已有缩略图；无法解码或超过输入像素限制的文件计入失败。
- 使用缩略图或缩小图，适合语义召回，不适合 OCR、细小物体识别或精确颜色判断。
- 仅将图片元数据变化作为增量依据。原文件在外部变化后应先重新扫描图库，再更新 AI 索引。
- 相似度是排名指标，不是识别置信度；即使描述没有对应内容，也可能返回最接近的候选。
- 有效索引数量为最近一次 AI 操作的快照。失效向量在检索时排除；当前没有自动压缩旁路索引的功能。
- 内存开销以 ONNX 会话为主：实测单个搜图 Worker 的 RSS 约为 900 MB（只载文本）～1170 MB（文本 + 视觉），其中视觉编码器约 270 MB——远大于它 95 MB 的模型文件，ONNX 会话的开销约为权重的三倍，这也是「单份索引就能把可用内存压到个位数 MB」的来源。可用内存紧张的机器上，「人脸索引 + 中途搜图」虽然不会崩，但仍会把进程推高（实测全程峰值 RSS 约 1.09 GB）；本轮未做 ONNX arena / 线程数调优。
